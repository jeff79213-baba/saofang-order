# 民宿掃房順序系統 — 設計規格 v2（增修）

> **本文件為 v2，補充／修訂 v1**（`2026-11-03-民宿掃房順序系統-design.md`）。未提及處一律沿用 v1。
> v2 聚焦：自訂房號、樓層自訂打掃順序、帳號管理（Cloud Function／保留區）、UI 微調。
> 房號格式決策：**純數字（3–4 位）**。自訂順序：**只存當日**。帳號：**加 Cloud Function 完整管理**。

---

## A. 房間資料模型（重大變更）

### A.1 穩定 ID + 可編輯房號
房號不再是「樓層×100+序號」，改為可自訂。為避免改房號時當天狀態遺失，房間改用**穩定 ID**：

```
sq-rooms/{id}            id = `${building}-${crypto.randomUUID()}`（例：A-9f3c2a10）
  { building: 'A'|'B', floor: 1|2|3|5, no: '105', enabled: boolean }
                         // floor = 顯示在哪一層；no = 可編輯顯示房號
```

- `no`：**純數字、3–4 位**、**同館唯一**（例如一館可同時有 102/105/106/107，但不可兩個 102）。
- `floor` 仍為 1/2/3/5（決定顯示在哪個樓層區塊），與 `no` 無數學關係。
- 排序（同級）改用 `no` 數字大小。

### A.2 當日狀態與順序
```
sq-days/{day}/rooms/{id}     // 鍵值改為穩定 id，其餘欄位同 v1
sq-days/{day}/orders/{floorId}   floorId = `${building}-${floor}`（例：B-3）
  { ids: string[], updatedAt: number, updatedBy: string }   // 當日該層自訂順序（有序房間 id）
```
- 自訂順序**只存當日**，隔天自動失效（換日不複製 orders）。
- `ids` 內含已停用／不存在的 id 會被忽略；清單中沒有的可掃房會補在最後。

### A.3 遷移（目前無正式資料）
- 重寫 `scripts/seed.ts`：以新 ID 制建立 `sq-rooms`（依預設 layout 生成 56 筆，`no` = 樓層×100+序號）。
- 新增 `scripts/reset-data.mjs`：清空 `sq-days` 舊測試資料與舊 `sq-rooms`，再重新 seed。
- v1 測試用 `sq-days`（舊 id 制）一律清除。

## B. 設定頁（櫃台）— 房號清單

移除 v1 的「每層房數 0–20 步進器」。改為：

- 每館 × 每層一個**房號清單**區塊，列出該層所有房間的**可編輯房號輸入框**。
- 每列：`[房號輸入框] [🗑 刪除]`；區塊底部 `＋ 新增房間`（新增一列空輸入框，帶入建議值＝同層最大數字+1）。
- 即時顯示「一館 N 間 / 二館 N 間 / 合計 N 間」。
- 儲存（套用）前驗證：
  - 房號為 **3–4 位數字**；否則標紅並拒絕。
  - **同館不得重複**；重複標紅並拒絕。
- 套用動作（差異同步）：
  - 新列 → 建立 `sq-rooms` 文件（新穩定 id，enabled=true）＋在當日 `sq-days/{today}/rooms/{id}` 補一筆 `dirty`。
  - 改號 → 只更新該房 `no`（id 不變，當天狀態保留）。
  - 刪除 → 移除 `sq-rooms` 文件（當日 doc 一併刪除；該房不再顯示與排序）。**此為「刪除房間」，非停用**。
  - 仍需保留 v1 的「單間停用/恢復」開關（enabled）作為「暫時不賣」用途。
- 操作一律「先確認、再寫入」；失敗還原並 toast。

> 決策補充：刪除房間＝真的移除；停用房間＝保留但不出現。兩者並存，設定頁每列提供 `開關`（停用）與 `🗑`（刪除）。

## C. 樓層自訂打掃順序（當日）

- `FloorSection` 標題右側（「可掃 N / 共 M」旁）新增按鈕「**自訂順序**」（僅櫃台可見）。
- 點擊開啟底部 sheet：列出該層**可掃房**（arriving/dirty，`enabled=true`），可**拖曳**排序（手機可上下移動按鈕）。
- 儲存 → 寫入 `sq-days/{day}/orders/{building}-{floor}`。提供「**清除自訂（回自動）**」。
- 排序規則（`buildQueue`）：若該層有 orders，則：
  1. 先依 `ids` 順序排列，`ids` 中不存在或已不可掃者略過；
  2. 不在 `ids` 中的可掃房，依 v1 自動排序補在最後。
- `orders` 為當日專屬，換日不複製。

## D. 帳號管理（Cloud Function + 保留區）

### D.1 資料
```
sq-staff/{uid}   { role: 'front'|'housekeeping', name: string,
                   disabled?: boolean, deleted?: boolean,
                   deletedAt?: number, createdAt?: number }
```
- `deleted=true` → 在「保留區」，前端無法取得角色（視為未授權）。
- `disabled=true` → 停用（可與 deleted 並用）。

### D.2 Cloud Function
- 新增獨立 functions codebase `saofang`（不影響既有 `shift` codebase），一支 **callable** `saofangApi`。
- 驗證：`context.auth` 存在，且 `sq-staff/{context.auth.uid}` 的 `role=='front'`、`deleted!=true`、`disabled!=true`；否則 `permission-denied`。
- 動作（`data.action`）：
  | action | 說明 |
  |---|---|
  | `list` | 列出全部帳號：`uid, email, role, name, disabled, deleted, createdAt`（以 Admin Auth listUsers + 合併 sq-staff） |
  | `create` | `{username, password, role, name}` → 建立 `username@saofang.local` Auth 使用者（emailVerified=true）＋寫 `sq-staff` |
  | `setRole` | 改角色 |
  | `disable` | `disabled=true` ＋ Auth `disabled=true`（收回權限） |
  | `enable` | `disabled=false` ＋ Auth `disabled=false` |
  | `delete` | 進保留區：`deleted=true, deletedAt=now` ＋ Auth `disabled=true` |
  | `restore` | `deleted=false` ＋ Auth `disabled=false` |
  | `purge` | 永久刪除：Auth `deleteUser` ＋ 刪 `sq-staff` 文件 |
- 使用者名稱規則：3–20 字、英數（大寫可）；密碼 ≥ 6 字。email = `${username}@saofang.local`。
- 不可把自己刪除/停用（Function 擋）。

### D.3 前端「帳號管理」頁（櫃台限定）
- 由 Settings 頁進入或獨立頁。
- 列表：帳號、角色、姓名、狀態徽章（正常／停用／保留區）。
- 每列操作：改角色、停用／啟用、刪除（保留區）、復原、永久刪除（保留區列）。
- 頂部「新增帳號」表單（使用者名稱、密碼、角色、姓名）。
- 密碼欄位遵守 AGENTS.md：附顯示/隱藏切換。
- 呼叫方式：`getFunctions` + `httpsCallable('saofangApi')`（`firebase/functions`）。DEMO 模式（mock）時此頁以記憶體模擬。

### D.4 部署
- `functions/` 目錄（獨立 package.json，nodejs 22），`firebase.json` 加 `functions` 設定（codebase `saofang`）。
- 部署：`firebase deploy --only functions:saofang`。
- Functions codebase 為 `saofang`，與班表 `shift` 互不影響。

## E. 排序演算法更新

```ts
export function buildQueue(
  rooms: RoomState[],
  customOrder?: string[],
): Array<{ room: RoomState; seq: number }>
```
- 無 `customOrder`：同 v1（tier → 剛退房 → 尚未打掃，1/2/3/4）。
- 有 `customOrder`：僅取可掃房，先依 `customOrder` 索引排序，未列者依 v1 規則補後。
- v1 全部測試案例維持；新增自訂順序案例：
  1. 給定順序 `[c,a]`，可掃房 `a,b,c` → 輸出 `c,a,b`。
  2. 順序含不存在的 id → 忽略。
  3. 順序未含某可掃房 → 該房排最後（依房號）。
  4. `customOrder=[]` 或未提供 → 同 v1 自動排序。

## F. 主畫面 UI 微調

- **Header**：移除日期旁的「N 間」文字。
- **卡片「✓」按鈕**（櫃台、一般模式）：卡片右上或底部新增小 `✓`；點擊 → `prevStatus=status; status='clean'`；對 `clean` 房再點 → 復原 `prevStatus ?? 'dirty'`。`occupied` 房不顯示（鎖定）。
- **後續入住標籤**：標記後改為**高對比實心琥珀**（`bg-amber-400 text-amber-950 border border-amber-500 font-semibold`），標記瞬間加 `scale` 動畫（`transition`）。不加 toast。
- 打掃模式的既有行為不變。

## H. Firestore Rules 追加（合併進共用 opencode-sk，勿覆蓋他人段落）

```
match /sq-days/{day}/orders/{floorId} {
  allow read: if sqSignedIn();
  allow create, update: if sqSignedIn() && sqRole() == 'front';
  allow delete: if sqSignedIn() && sqRole() == 'front';
}
```
- `sq-staff` 維持 `read: signedIn`、`write: false`（由 Function 以 Admin 寫）。
- 動 rules 一律走 `npm run deploy:safe`（含漂移檢查）。
